how does the new ssr features help the sitegen process, in a nutshell

It collapses most of the enhanced-prerender pipeline into a function call. The capture stage — Vite preview server, Playwright, Chromium, bounded capture concurrency, readiness handshake, capture-entry removal — is replaced by a build loop calling renderPage(request) per planned route and Server.injectIntoTemplate. That kills four of my findings outright: no browser means no Chromium sandbox conflict inside alchemy deploy, no nondeterminism to pin or normalize away, no readiness protocol, and no outerHTML property-loss bug (the server renderer has an explicit controlled-state contract for value/checked/selected/muted). isHydratable: false then delivers "static routes ship no Foldkit runtime" as an upstream guarantee rather than something URM enforces after the fact with a scanner and bundle inspection, so the six validation rules become assertions about your own emitter instead of forensics on captured markup. Builds get fast and cheap enough to run anywhere, which makes the sandboxed-worker security boundary practical again. What it does not touch: the deployment layer is unchanged, so rollback, memoization-vs-build-record, and the CLI boundary findings all stand; widgets still can't server-render (makeElement/embed are client-only), so the enhanced/foldkit widget modes keep their current shape; and the price is a coordinated upgrade — foldkit 0.144→0.151, @foldkit/vite-plugin 0.13→0.17, effect rc.108→rc.111.
